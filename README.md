# 求职工具链：投递副驾驶 + 面试教练

两个可复用的 AI 工作流。一个解决「把岗位筛干净」，一个解决「把面试练扎实」。

这不是演示原型——是我本人在求职期间每天在跑的生产工具，覆盖了从找岗、打分、改简历、投递跟踪，到刷题、弱项归档的完整闭环。

---

## 为什么做

求职最耗时的不是写简历，是**重复判断**。

- 一个岗位值不值得投，要读完整 JD、比对自身经历、判断硬门槛是否卡死。人工做一次 20 分钟，一天看 10 个就是 3 小时，而且判断标准会漂移——今天觉得能投的，明天又觉得不行。
- 面试同理。题刷了，但错在哪、下次会不会再错，全凭记忆。

这两件事的共同点是：**规则可以显式化，判断可以留痕**。所以我把它们各做成一个工作流：读 JD 打分入池、排序出推荐；刷题记录得分、薄弱点归档、下轮优先出没练过的题。

**一岗一版的边际成本，是这个技能真正的价值锚点。** 写一份简历一年一次，而一岗一版是每个岗位都要做一次的——把它的成本从两小时压到十分钟，才是值得做工具的地方。

## 项目一 · 求职投递副驾驶

```
找岗入库 → 三档打分 → 排序推荐 List → 选模板组版 → ATS 自检 → 台账跟踪 → 复盘回喂
```

### 核心设计：硬门槛与软匹配分离

把「能不能投」和「有多匹配」拆成两个独立层，这是整个打分体系的支点。

**第一层 · 硬门槛一票否决**（红 / 黄 / 绿三档）
年限、院校、城市、岗位是否已下线——任一条卡死直接进红档，**不进推荐列表**。红档不看分数，分数再高也不投。

**第二层 · 软匹配打分**（只对绿档 / 黄档算）

```
匹配分 = 档位基础分（🟢20 / 🟡0）+ 双向覆盖率 × 80
```

这里有两个刻意的设计：

1. **覆盖率是分本体，档位只是确认加分。** 早期版本给档位 60 分权重，结果一个 JD 写得漂亮但实际命中寥寥的岗位也能排进前列。改成覆盖率主导后，排序才反映真实匹配度。
2. **必须双向比对。** 旧口径只统计「JD 侧写了多少词」，不比对简历——这会系统性高估那些 JD 罗列一大堆关键词的岗位。现在只有「JD 有 ∧ 简历有」才计命中。

### 另设一个不进分数的指标：必备层覆盖

「这岗我命中多」和「这岗的硬门槛我够了」是两件事。所以必备层（JD 里去掉「…者优先」的硬性条款）单独统计成 `命中/必备总数`，**不参与匹配分**，低于 50% 直接标 ⚠️。

### JD 完整性闸门

**残缺 JD 的缺口数是「未探明」，不是 0。** 源文本缺了大半时，探不到缺口不等于没有缺口。检出截断痕迹的岗位会被显式标记，提醒人工补录，而不是被当成「零缺口完美匹配」。

### 岗位下线判定：精确优先

能自动判定「已结束 / 已下线」，但不能证实「仍在招」——正文无下线词只说明当时没读到。

词表只收岗位语境下才出现的短语。这条规则是被教训换来的：早期词表收录了宽泛的「404」，一次误杀 9 个在招岗位。**宁可漏检交人工，不可误杀好岗。**

## 项目二 · AI 产品经理面试教练

```
出题（避开已练过的）→ 作答 → 按星级标准点评 → 追问 → 薄弱点归档 → 下轮优先补弱项
```

### 题库的来源分级

题库每道题必须带来源，无出处的一律如实标注。当前 138 题中，有可查出处 104 题（75.4%），模型生成且无外部出处 34 题（24.6%）——这 34 题在审计报告里**逐题列名，不隐去**。

来源分六类，可信度递减：真题出处 > 用户喂题 > 一手项目 > 考点出处 > JD 能力出处 > 模型生成。

规则是硬的：**新题只能来自联网调研或用户喂题，不得凭空生成入库。** 曾有 65 道题无出处被指出违反了这条原始需求，之后才补上来源审计这份报告。

### 评分与弱项归档

每题按星级（★–★★★★★）定难度与作答时长标准。作答后记录得分与薄弱点关键词，跨会话累积成弱项档案；下次出题优先出弱项所属的域，且**先查已出题清单避免重复**。

同时维护「进行中」断点：中途被打断不算收尾，下次启动自动续上那道题，不丢进度。

## 我怎么验证它们有效

- **打分口径**：用 35 份真实 JD 模拟四套权重方案，找出排序拐点后再定稿（v1 档位主导 → v3 覆盖率主导），不靠直觉拍权重。
- **防回归**：核心脚本配 pytest 用例，改动后跑全量回归，避免「修一处坏一处」。
- **简历产出**：每份派生稿过 ATS 自检（查占位符与死词），不通过不出稿。
- **题库**：来源审计报告随题库更新重跑，出处状态如实暴露。

## 踩过的坑

**权重改了，系数没改。** 调参时只改了基础分，漏改覆盖率权重，导致写回分数用的是「新基础分 + 旧权重」的混合口径，和模拟结果完全对不上。教训：权重的唯一真源必须收敛到一处，禁止在多个脚本里各写一份。

**把推测当事实。** 早期策略文档按记忆反推出一段空窗年限，和事实库口径冲突，一路带进了简历。之后定的规则是：策略文档里没有来源标注的「事实」，默认是待确认，不是已确认；口径唯一真源是事实库。

**下线词表过宽误杀好岗。** 见上文「精确优先」。

**题库无出处。** 见上文「来源分级」。

## 安装与依赖

两个技能均为「说明文档 + Python 脚本」形态，脚本只依赖 Python 标准库。

**外部数据目录**（脚本按约定路径读取，需自建）：

| 路径 | 用途 |
|---|---|
| `~/.workbuddy/career-facts/` | 事实库：`profile.md`（信息与求职意向）、`experiences.md`（原子经历）、`projects.md`（项目库）、`metrics.md`（数字台账，每个数字带口径与来源）、`tags.md`（标签体系） |
| `~/WorkBuddy/job_seeking/strategy.md` | 分轮投递策略（占坑 / 练手 / 熟流程 / 主攻），技能只读 |

**设计原则**：事实与策略分离。事实库只增不改、由人维护；技能只读引用，不得改写。所有量化指标必须能在 `metrics.md` 找到出处，否则不允许出现在任何产出里。
