# jd-pool —— 岗位池

## 三档结论（硬门槛一票否决）

| 档位 | 含义 | 处置 |
|---|---|---|
| 🟢 green | 无硬门槛冲突，匹配度达标 | 进推荐排序 |
| 🟡 yellow | 存在可核实的软性疑虑（年限、行业、薪资带） | 进排序但标注待核实 |
| 🔴 red | 命中一票否决项（硬性年限、院校、城市冲突、岗位已下线） | 不进推荐 List |

**红档不参与排序**——分数高不代表能投，硬门槛是前置条件。这是「一票否决」与「软匹配打分」两层设计的分工。

## 文件格式

每个 JD 一个 markdown 文件，首行为机读元数据：

```
<!-- MATCHMETA tier=green score=75.0 coverage=6+2/9·18 company=... title=... date=... source=... url=... mode=bi hit=6 fill=2 gap=1 must=3/5 truncated=0 -->
```

| 字段 | 含义 |
|---|---|
| `tier` | 档位结论 |
| `score` | 匹配分 = 档位基础分（🟢20 / 🟡0）+ 双向覆盖率 × 80 |
| `coverage` | 已命中 + 可补缺口 / JD 提及类目 · 总类目 |
| `mode` | 打分模式（`bi` = 双向比对简历与事实库） |
| `hit` / `fill` / `gap` | 命中 / 可补（事实库有证据）/ 真缺 |
| `must` | 必备层覆盖（独立指标，不进匹配分） |
| `truncated` | JD 完整性闸门：源文本是否检出截断 |

正文依次是硬门槛检查、双向匹配结果、技能点层级分析（必备 / 优先 / 加分项三层切分）。

## 关于完整性闸门

残缺 JD 的缺口数是「**未探明**」而不是 0。源文本缺了大半时，探不到缺口 ≠ 没有缺口。
`truncated=1` 的岗位会显式标记，提醒人工补录而非当作「零缺口」。

## 本仓库的示例文件

`examples/` 下放了 2 份已脱敏的示例 JD，用于展示输出格式。
原始岗位池含个人投递策略与进度记录，不随仓库分发。
