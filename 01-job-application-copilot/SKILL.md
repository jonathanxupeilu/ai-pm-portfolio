# 求职投递副驾驶（job-application-copilot）

## 定位

**求职 CRM，不是简历生成器。** 写一份简历一年一次，真正的工作量在一岗一版——本技能的价值锚点是**把一岗一版的边际成本压到 10 分钟**：主动找岗入库 → 三档打分出匹配分 → 排序推荐 List → 按企业类型选模板 → 按标签组版 → ATS 自检 → 台账跟踪 → 复盘回喂。

## 最重要的边界：career-facts 事实库

**位置**：`~/.workbuddy/career-facts/`（即 Windows 的 `%USERPROFILE%\.workbuddy\career-facts\`，不在 skills 目录下，避免被当技能扫描）

| 文件 | 内容 |
|---|---|
| `profile.md` | 个人信息、教育、求职意向、年限硬门槛现状、空窗期口径、定位摘要 |
| `experiences.md` | 原子经历条目（E-xx），含角色动词/标签/指标关联，及**简历收录决议**（哪些进哪些不进） |
| `projects.md` | 项目库（P-xx），含面试弹药、保密级别与脱敏要求、**简历收录决议** |
| `metrics.md` | 数字台账（M-xx），**每个数字必须带口径+来源+性质（实测/目标/行业数据）**；含「曾误用已纠正」留档区 |
| `tags.md` | 标签体系——一岗一版按 JD 关键词筛 tag 组版的依据 |

### 维护规则（硬约束，违反=事故）

1. **事实库由用户本人维护，技能只读引用。** 生成简历、打分、组版时只能引用其中条目，**不得改写**。
2. 用户说「更新某条/加一条经历/新数字」时：AI 按 schema 格式化 → **展示给用户确认 → 用户点头后才写入**。不确认不落盘。
3. 用户可直接编辑这些文件（记事本/任意编辑器均可），改完技能下次读取即生效。
4. **数字铁律**：没有口径与来源的数字不得写入 metrics.md，更不得出现在任何简历版本里。目标值≠实测值，行业数据≠个人成果——metrics.md 设「曾误用已纠正」留档区，翻车案例一律留档，不许重演。
5. **简历收录决议以 experiences.md / projects.md 内的决议表为准**：P-03 个人知识产品暂不放，E-03 已砍，E-08/E-09 合并讲，P-05 纳入。组版引擎照此执行，用户改决议时同步更新决议表。
6. **与 ai-pm-interview-coach 共享**：两个技能引用同一事实库，项目名/数字只有一个真源，禁止各自另存副本（历史教训：「AI股票分析系统」vs「深度投研决策系统」两名并存）。

## 证据铁律（本技能的红线）

> 任何策略结论、匹配判断、市场判断，**不得依赖大模型自身记忆**。必须挂以下三类证据之一：
> 1. **WebSearch/WebFetch 原文 URL**（主源）
> 2. **IMA 知识库检索结果**（辅助源，仅摘要级——PDF 全文有权限墙，引用时必须标注「IMA 摘要级引用」，不得假装读过全文）
> 3. **career-facts 条目 ID**（E-xx / P-xx / M-xx）
>
> 凭模型记忆给出的判断一律标注「无外部依据，仅供参考」，且不得作为投递决策唯一依据。找不到证据就说找不到，不编造（历史教训：曾有 65 道题库题目无出处，被使用者指出违反了「必须有来源」的原始需求）。

### 口径唯一真源（防版本漂移）

**时间、年限、空窗期一类口径，唯一真源是 `career-facts/` 与已定稿简历**；`references/` 策略文档是早期调研产物，含**未经确认的推测性数据**，引用前必须回事实库核对，冲突时以事实库为准并在策略文档中标注「已作废」。

> 实例：策略文档曾按记忆反推出一段空窗年限，与事实库口径冲突，最终以事实库为准、策略文档同步修正。**教训：策略文档里的"事实"若无来源标注，默认是待确认，不是已确认。**

## 一、主动找岗与 JD 入库

### 主动找岗流程（手动触发）

用户说「**找岗 / 搜岗位 / 帮我看看有什么坑**」时触发，按以下步骤跑一轮：

0. **接收定语（用户可指定过滤条件）**：用户可在「找岗」后附加定语——**年龄、相关年限、公司规模、行业、目标公司名单**等，例：「找岗 行业金融 公司500人以上 年限3年内」。定语当轮生效并在汇报摘要中标注；脚本内置年龄红线（JD 写年龄上限且候选人超线 → 直接红档），其余定语在搜索词与人工初筛时执行。常用定语建议用户写进 `career-facts/profile.md` 求职意向区（用户自维护），技能每轮读取作为默认过滤
1. **生成搜索词**：读 `career-facts/profile.md` 的求职意向与定位摘要，结合当轮定语，组合出搜索词矩阵——岗位词（AI产品经理/大模型产品经理/Agent产品经理）× 地域词（上海）× 行业词（按当轮侧重可选：金融科技/AI应用/互联网），每次轮换组合避免结果重复
2. **三通道搜索**（按下表优先级），来源一律标注 `主动搜索`
3. **逐个入库打分**：每条 JD 存为临时文件 → `match_jd.py <文件> --company X --title Y --save --source 主动搜索 --purpose <轮次>`（轮次见下方「分轮投递策略」）
4. **刷新排序**：跑 `rank_pool.py` 重新生成 RANKED_LIST.md
5. **汇报摘要**：对话里只给本轮结果摘要（新增几个、最高分是谁、红档几个），详情让用户看 RANKED_LIST.md

**触发方式是手动**——用户不发话不主动搜，不做定时自动化（已确认）。

### 轮次标注机制（分轮投递）

`match_jd.py --purpose` 支持五类标注（占坑 / 练手 / 熟流程 / 主攻 / **不投**），写入 MATCHMETA 的 `purpose=` 字段与档案行「轮次定位」。**`rank_pool.py` 会把轮次作为独立一列展示在榜单上**（无标注显示「—」）。缺省为空，不影响无策略的使用方式。

其中 **`不投` 不是策略轮次，是「显式排除」**：用于**真目标大厂的非点名岗**——档位可能很高（🟢），但按分轮纪律「严禁投真目标大厂（同岗半年冷却）」本轮不投。`rank_pool.py` 会把这类岗位从推荐排序剔除、单列「🚫 本轮不投」一节，**与「⛔ 已结束」区别开**（前者是策略排除=主观，后者是岗位失效=客观），JD 原文均保留。

> 回填暴露的另一条事实：**该批一份都不符合「练手」定义**（练手 = 初创/非目标中小 50-150 人、A 轮前后）。实测规模：浪潮 3.6 万人、云从 327 人、MiniMax 385 人、中数联 300~500 人——全部超上限。练手岗集中在 09-09/09-10 那批（所以那 18 份全带 `练手`）。**说明「空标注」未必是漏标，可能是当批口径使然**。

**轮次是三个独立维度之一，别混为一谈**：

| 维度 | 回答的问题 | 存在形式 |
|---|---|---|
| 档位 🟢🟡🔴 | 这个岗**能不能**投 | 目录 green/yellow/red |
| 匹配分 | 这个岗**配不配**你 | MATCHMETA 的 score |
| 轮次（purpose） | 这个岗**什么时候**投、准备多深 | MATCHMETA 的 purpose |

轮次标注**不改变分数、不改变档位**——它只影响投递时机与准备深度。

**用户的具体分轮策略（各轮投什么、目标行业、验收标准）是个人决策，不属于本技能**——正文存于**项目工作目录的 `strategy.md`**（用户自维护，技能只读）。**2026-09-10 已从 `career-facts/` 迁出**：它与用户手写的 `jd_raw/` 同级，属于「用户手写输入」，而 `career-facts/` 只放事实。

默认位置 `~/WorkBuddy/job_seeking/strategy.md`，脚本按以下顺序解析（`match_jd.find_strategy_file()`，唯一真源）：

1. `$JOB_SEEKING_DIR/strategy.md`（环境变量显式指定，最高优先）
2. `~/WorkBuddy/job_seeking/strategy.md`（默认项目目录）
3. `~/.workbuddy/career-facts/strategy.md`（旧位置，向后兼容，可安全删除）

- 找岗时**先读该文件**：有分轮策略 → 按当前轮次生成搜索词并标 `--purpose`；无该文件 → 按普通流程跑，不臆测轮次
- 轮次与三档判定是两个维度：轮次标注不改变打分结果，用户说升级就升级
- 该文件可作为找岗流程第 0 步「定语」的来源之一（公司规模 / 行业 / 轮次范围）

### 三通道（按优先级）

| 通道 | 适用 | 说明 |
|---|---|---|
| ① 猎聘官方 MCP | 已配置时首选 | 官方 SSE 服务，职位搜索/详情/推荐；配额 60次/分（搜索+查看+投递共用）；token 90 天过期需用户续 |
| ② 浏览器自动化 | BOSS直聘、拉勾等无 MCP 的平台 | 用 agent-browser 技能操作用户**本机已登录**的浏览器读 JD 页面。不走逆向 MCP/指纹伪装/自动打招呼——那违反平台协议，求职者账号被封是丢求职渠道 |
| ③ WebSearch + IMA | 兜底 | 搜聚合页/面经/JD 转载；IMA 检索行业报告与市场洞察（摘要级）。链接必须校验有效性，失效标「链接待核实」但保留 JD 原文摘录 |

### 入库规则

每个岗位一个 md，按三档存入 `jd-pool/{green,yellow,red}/`，命名 `公司_岗位_YYYYMMDD.md`。**用 match_jd.py --save 入库**（自动带 MATCHMETA 元数据行：档位/匹配分/覆盖率/公司/岗位/日期/来源/**url**，rank_pool.py 靠它排序），内容含：JD 原文摘录（匹配的依据）+ 链接 + 采集日 + 三档打分结果 + 关键词覆盖清单。用户直接投喂的 JD 用 `--source 用户投喂`。

**入库前必做两件事（2026-09-10 血泪教训）**：

1. **`--company` / `--title` 必须显式传**。不传会存成 `未知名公司_未知岗位_YYYYMMDD.md`，同一天跑多个岗位会**互相覆盖**，前面的白干（当天实测 3 个岗存成同名，前两个被第三个盖掉）。
2. **先查 URL 是否已入库，避免重复研究同一个坑**。脚本目前无去重，同一岗位换天抓会被二次入库，且因文本摘录不同可能判出**互相矛盾的档位**（实测：路客洲域 9-09 判 🟡，9-10 因摘录差异判 🔴）。查重办法：比对已有文件 MATCHMETA 的 `url=` 字段；重复时保留信息更全的那份，把新分析合并进去后删除重复件。

### JD 完整性闸门与补录通道（patch_jd.py，2026-09-10 新增）

**为什么有这一节**：抓取会因站点结构、反爬、分页等原因让 JD 残缺。陆家嘴金融AI 那份丢了整个「任职要求 + 加分项」段（存档正文 826 字符，实为 3393），系统却报「**真缺口 0 ｜ 无**」——把「没查到」伪装成了「查过了，没有」。截图里 21 个真实技术缺口（RLHF / DPO / ReAct / LangChain / CrewAI / CFA…）一个都没探到。**残缺不可怕，假装完整才是。**

#### 闸门：三条判据，任一命中即标残缺

| 判据 | 说明 |
|---|---|
| ① 截断痕迹 | 正文含中文截断标记（「快照在此截断」「原文未抓全」…）。**只看它是否落在正文尾部 85% 之后**——补录后原提示留在中段、其后仍有内容，即视为已补录。**不收英文 truncated**（实测被 Vue 模板残留 `{{ truncatedJobTitle3 }}` 带偏） |
| ② 结构缺失 | 有「岗位职责」段却无「任职要求/加分项」段，且正文 < 1200 字符 → 典型抓取截断 |
| ③ 正文过短 | < 300 字符，不足以支撑打分 |

命中后分两级写进 MATCHMETA 的 `truncated=`：`1`（判据①③，硬证据）/ `suspect`（判据②，结构可疑）。`rank_pool.py` 在榜单缺口列显示 ⚠️ / ❓。

**核心语义**：残缺时缺口数报「**未探明**」而非 0，榜单上写作 `**1** / 0 / 0 ⚠️JD残缺·未探明`。**0 是「查过了没有」，未探明是「根本没查到」——投递决策不能混为一谈。**

> 判据纪律：**宁可漏检，不可误杀**。实测否决过一条「末行突兀」判据（正文不以句号结尾=疑似截断），全池误杀 10/35=28%——末行常是福利标签（「六险一金」「周末双休」），天然不带句号。

#### 补录通道：patch_jd.py

```bash
python scripts/patch_jd.py <档案路径> --refetch        # 按 META 的 url 回源重抓（推荐）
python scripts/patch_jd.py --refetch-all [--dry-run]   # 批量修全池 truncated 档案
python scripts/patch_jd.py <档案路径> --from-file <txt> --source "用户截图"   # 手工补录
python scripts/patch_jd.py <档案路径> --list           # 查看已有补录段
```

补完走 `rescore_pool.py --apply` 重算——**完整性由闸门重新判定，补录脚本不给自己发合格证**。

三个必须知道的实现点：

1. **内容追加进「JD 原文摘录」的同一个代码块内**，不新开一节——`rescore_pool.py` 靠该锚点取正文，新开一节它读不到。
2. **插入点必须在【人工复核备注】之前**。打分与重算都按 `split("【人工复核备注】")[0]` 取正文（备注是 AI 批注、不参与打分）；补录段若落在备注之后就**会被这刀切掉，补了等于没补**（实测踩过）。
3. **幂等**：按内容 sha 去重，重复跑不会灌水。

**实战效果（2026-09-10 批量补录 4 份）**：

| 岗位 | 正文 | 匹配分 | 命中/可补/真缺 |
|---|---|---|---|
| 陆家嘴金融AI | 826 → 3393 字 | 44.4 → **64.4** | 10/0/0（假零缺口）→ 14/1/1 |
| 薪合信息科技 | 259 → 5464 字 | 15.6 → **46.7** | 3/1/1 → 9/3/1 |
| 徐汇某AINative | 538 → 2965 字 | 57.8 → **73.3** | 11/2/0 |
| 长宁某工业AI | 576 → 2326 字 | 60.0 → **73.3** | 11/2/0 |

**回源抓取的两个坑**：① 站点 WAF 拦 `WebFetch`（返回 418），但 `urllib`/`curl` 带 UA 能正常取到 SSR 页面；② 页脚会把 Vue 模板残留（`{{ }}`、`@click`、`-->`）抓进正文，脚本已按 `JUNK_PAT` 过滤。SPA 站（zhipin / neodrop 等）正文不在 HTML 里，`--refetch` 报「解析正文 0 字符」，需走 `--from-file` 手工补录。

> ⚠️ 注意：**补录会让匹配分上升**（残文分低）。这意味着榜单上排后面的岗位未必更差，可能是 JD 更残。看榜单时先看缺口列的 ⚠️ / ❓ 标记。

### 脚本的语义盲区（规则判不到的，人工必须复核）

`match_jd.py` 是**规则版**引擎，只认年限数字，读不懂从句。以下两种写法它都会误判，必须人工覆盖并在文件里写明理由：

| JD 原文写法 | 脚本判 | 人工应判 | 理由 |
|---|---|---|---|
| 「1-3 年产品经验，**优秀应届生也可以考虑**」 | 🔴（取上限 3 当硬门槛） | 非年限硬伤 | 是**上限宽松**表述，不是「≥3 年且必须」 |
| 「3 年左右…经验，**能力突出者不受年限限制**」 | 🔴 | 🟡 可论证项 | 有明确豁免条款，不满足红档触发条件「年限 ≥3 年**且写必须**」 |

**人工覆盖档位时**：改 MATCHMETA 的 `tier=` / `score=`（score = 档位基础分 green 20 / yellow 0 + 覆盖率 × 80），把文件移到对应档位目录，并在正文写明「人工复核覆盖说明」——原判、误判原因、真实结论。**不允许悄悄改分不说明。**

### 投递链接规则（用户要能一键点进去投）

- **链接是结构化字段，不是埋在正文里的文本**：`--save` 时自动从 JD 文本提取（优先「链接：」后的那个），也可用 `--url <链接>` 显式指定；写入 MATCHMETA 的 `url=`，并在岗位文件顶部生成 `- **投递入口**：[点击投递 → 公司 · 岗位](url)`
- **RANKED_LIST.md 的「投递链接」列可直接点击**，不用先打开 md 再翻原文
- **链接校验的能力边界（2026-09-10 重写，旧结论有误）**：猎聘/BOSS/全职招聘网/国聘/腾讯招聘是前端渲染站点，任何 `/job/*` 路径都返回 200（实测 `quanzhi.com/job/THIS_IS_A_FAKE_ID_123` 也是 200）。但**这不等于「只能人工确认」**——旧版本据此对这类站点直接放弃正文检测，导致两个已下线岗位漏检。现行做法：
  - **① URL 先规范化**：移动端壳域名换桌面端。`m.quanzhi.com/job/detail/<id>` 只回 3912B 空壳页（无 title 无正文），换 `www.quanzhi.com/job/<id>` 回 50KB 服务端渲染完整页 → 可直接判定
  - **② 200 响应一律 GET 正文扫下线词**（不再按站点类型跳过）。词表含「已结束 / 已下线 / 停止招聘 / 职位已结束」等，岗位详情页出现这些词基本就是下线
  - **③ 读足量字节**：`_fetch` 的 GET 读 200000 字节。旧版读 20000，而实测页面里「已结束」的字节位置在 17810~28227 不等——**有的岗位两处全在 20000 之外，只读前 20000 会静默漏检**（日志看着像扫过了）
  - **④ 判不了的才降级**：正文读不到（空壳页 `<12KB`）或读到但无下线词，标 **❔ 需人工点开确认**，不谎报「正常」
  - 能自动判定**下线**；**不能证实仍在招**——正文无下线词只说明暂时没读到
  - **链接失效 ≠ 岗位失效**：JD 原文摘录才是匹配依据，失效只提示不自动删档
- **已结束岗位不进推荐排序**：标 `status=dead`（META）或校验判 dead 的，从「推荐投递排序」移到榜单末尾「⛔ 已结束 / 不可投递」独立小节——**JD 原文保留**（可作岗位画像与组版语料），但不再占投递位
- **手上有确认情报时直接标 META `status=dead`**，比等联网校验更快更准（`check_link` 的 `meta_dead` 参数优先于网络请求）
- 抓不到链接的岗位标「⚠️ 未抓到链接，需人工补」，仍可正常参与排序

### 岗位池清理（cleanup_pool.py）

池子只进不出会堆垃圾。规则（**默认 dry-run，必须 `--apply` 才真动文件**）：

| 类型 | 规则 | 动作 |
|---|---|---|
| **过时** | 采集日距今 > 60 天（`--stale-days` 可调） | 移入 `jd-pool/archive/YYYY/`（不删除，可回溯），不再进 List |
| **冗余** | 同「公司 + 岗位名」重复入库 | 保留匹配分最高者（同分保留最新），其余归档 |
| **黑名单** | 🔴 red 档 | **长期保留，永不过期**——它的价值是防重复研究同一个坑（如岗位写死年龄上限、候选人超线这类硬伤）；`--check-block` 打印黑名单键，新搜到同名岗位直接跳过、不重复打分 |
| **链接失效** | 404/410 | 只标提示，**不作为清理依据**（原则同上） |

日常：`python cleanup_pool.py` 预览 → 确认无异议 → 加 `--apply` 执行 → 重跑 `rank_pool.py` 刷新。RANKED_LIST 里采集满 30 天会自动标「⚠️ 待复核」。

### 排序推荐 List（jd-pool 的呈现方式）

`jd-pool/RANKED_LIST.md` 是岗位池对用户的主呈现——**按匹配分降序的推荐 list**，不是一堆散文件：

- 匹配分 = 档位基础分（🟢20 / 🟡0）+ **双向**关键词覆盖率 × 80，体现简历与能力的匹配度
  - 语义：**覆盖率是匹配分本体，档位只是对 green 的「确认加分」**（green 硬门槛全过额外 +20）
  - 上限：green 满分 100，yellow 满分 80（yellow 本身有硬伤，不该能拿满分）
  - 权重唯一真源在 `match_jd.py` 的 `TIER_BASE` / `COVERAGE_WEIGHT`；`rescore_pool.py` / `rank_pool.py` 均从这里取，**禁止在任何脚本里硬编码权重数字**（2026-09-10 踩坑：只改了 rescore 的 base 漏改权重系数，导致写回分数用「新 base + 旧权重」的混合口径，与模拟结果完全不符）
  - 2026-09-10 调权两轮：v1 🟢60/🟡35 + ×40（档位主导）→ v2 🟢50/🟡25 + ×50（仍不够，green 命中 0 类也有 50 分）→ v3 🟢20/🟡0 + ×80（现行）。用 35 份真实 JD 模拟四方案后的拐点：命中 12+补 2 的某证券从第 11 名升至第 6 名首次进入主力区，Top3 保持稳定
- 🟢🟡 进排序表（排名/匹配分/档位/轮次/公司岗位/投递链接/命中·可补·真缺/**必备层**/采集日/时效/来源/详情文件）+ 每条的下一步动作
  - **必备层列**（2026-09-10 新增）：`命中/必备总数（百分比）`，独立指标不进匹配分；<50% 标 ⚠️。让人一眼区分「这岗我命中多」与「这岗的硬门槛我够了」
- 🔴 不进 list，末尾只报存档计数（别投的坑防重复研究）
- 另有 **🚫 本轮不投** 分区（`purpose=不投` 的策略性排除，如真目标大厂的非点名岗）与 **⛔ 已结束** 分区（`status=dead`）——前者主观排除、后者客观失效，都保留 JD 原文但不占投递位
- 每次 match_jd.py --save 入库后必须重跑 rank_pool.py 刷新；缺元数据的旧文件归「待补分」区并提示重跑
- 分数只用于排序，投递决策仍以三档结论 + 人工判断为准

### 关键词库沉淀（mine_keywords.py）

`SOFT_KEYWORDS` 的 18 类词表最初是拍脑袋定的（2026-09-10 从 16 类扩到 18 类，新增技术架构、交付落地/迭代）。池子里有几十份真实 JD，应该让数据说话：

```
python scripts/mine_keywords.py --df 3 --top 20 --save   # 落盘 jd-pool/KEYWORD_MINING.md
```

双轨输出：
- **A 轨（词典匹配）**：187 词领域词典 × 真实 JD 频次，结果可靠，是决策依据。
  同时给**反向信号**——词典里有但市场几乎不提的词，不值得花组版篇幅。
- **B 轨（n-gram 探索）**：纯统计挖词，能发现词典外新词，但会产出「产品的」这类碎片，**只作线索需人工判**。

铁律：**脚本不自动改词表**。发现未覆盖高频词后，人工分三类处理——
① 真实能力要求 → 加进 `SOFT_KEYWORDS`；② 简历有证据 → 组版时写进去；③ 确实没有 → 承认真缺口。

## 二、三档打分（match_jd.py 的规则，脚本前先人工按此判）

**先硬门槛，后软匹配，顺序不可反。**

| 档 | 触发条件（任一命中） | 动作 |
|---|---|---|
| 🔴 red 别投 | 年限 ≥3 年且写"必须"；硬卡 985/211 本科；非上海且不支持远程 | 存 red/ + 一句话劝退理由（防重复研究同一个坑），不出简历 |
| 🟡 yellow 改造后投 | 年限要求高于候选人实际经验；要求"2 个以上 AI 落地案例"等可论证项 | 存 yellow/ + 差距分析 + 曲线路径建议（内推/作品集打动）+ 针对性改写方向 |
| 🟢 green 投 | 硬门槛全过 | 存 green/ + 软匹配关键词覆盖率 + 一岗一版简历 |

**打分必须诚实**：硬伤就标红，不报虚假的高匹配度。用户投 50 家全挂还不知道为什么，是这个技能最大的失败。

### 双向匹配（2026-09-10 起的默认口径，务必理解）

老口径只在 JD 文本里搜关键词，回答的是「**这份 JD 写得全不全**」——**不是「你配不配」**。
后果：JD 写得花哨的岗位排前面，真正匹配你的朴素岗位反而靠后。这是 RANKED_LIST 的系统性偏差。

新口径对每一类关键词做三方比对：

| 类别 | 判定 | 计分 | 组版动作 |
|---|---|---|---|
| ✅ **已命中** | JD 有 ∧ 简历有 | 1.0 | 保持；注意看落在技能清单还是项目实证（分量不同） |
| 🔧 **可补缺口** | JD 有 ∧ 简历无 ∧ 事实库有证据 | 0.5 | **组版时必须补进简历**，不得编造新事实 |
| ⬜ **真缺口** | JD 有 ∧ 简历无 ∧ 事实库也无 | 0 | **不补**，面试用诚实说法兜底 |

`coverage` 字段格式：`已命中+可补缺口 / JD提及类目·总类目`（如 `7+2/10·16`）。

用法：`python scripts/match_jd.py <jd文件> ... --save`（默认已开双向，简历取 `resumes/baseline_v4.md`）；
`--resume <路径>` 指定别的简历；`--resume none` 退回旧的单端口径（仅诊断用）。

**命中 ≠ 有分量**：脚本会打印每条命中的简历出处（落在哪个章节）。
「技能清单里列了个词」和「项目经历里有量化实证」含金量完全不同，组版时优先把后者摆到前面。

### 打分规则升级后的全池重跑（rescore_pool.py）

改了打分规则，存量 JD 的分数还是旧口径算的——**新旧分混排 = 排序无意义**，必须全量重跑：

```
python scripts/rescore_pool.py            # dry-run：先出对账报告看分数变化
python scripts/rescore_pool.py --apply    # 确认后写回
python scripts/rescore_pool.py --recheck-gate  # 附带输出档位重判参考意见（不改分数）
```

安全约束（都是踩过的坑）：
1. 默认 dry-run，`--apply` 才写；脚本幂等，可重复运行
2. **不重判硬门槛**：存量 JD 的「原文摘录」里混进过 AI 批注（某证券那条写着
   「40-70k 上海 **5-10年** 本科（**列表页标注；任职要求写2年+…**）」，括号里是批注不是 JD 原文），
   重跑 hard_gate 会读到批注里的年限，把人工判定的 yellow 误打成 red。
   硬门槛结论已有首次判定 + 人工复核背书，不该被存档污染推翻。
3. `manual=1` 的 JD 保留其人工判定的档位，但分数与双向数据照常重算（保护档位，不保护分数）
4. 档位存疑时不移动文件（rank_pool.py 以所在目录判定档位，擅自移动会让 RANKED_LIST 路径失效）

> **采集铁律（由 2 引申）**：JD 原文摘录区只放原文，任何 AI 批注/推断一律写进 `【人工复核备注】` 段。
> match_jd.py 打分时会剔除该段，但 rescore 读的是摘录区——混进批注就会污染后续每一次重跑。

### 三层语义切分与细粒度技能点（P1，2026-09-10 新增）

**背景**：18 个 `SOFT_KEYWORDS` 类目太粗，且对 JD 的三层约束力一视同仁。JD 写「任职要求 3. 三年以上经验」和「加分项 5. 有 CFA」约束力天差地别，但旧口径都只算「JD 提到了」。后果是一份加分项堆满的 JD 会把分数抬上去，候选人误以为那些是硬门槛。

**两层新结构**（都在 `match_jd.py`，由 `rescore_pool.py` 重算、`rank_pool.py` 呈现）：

1. **`segment_jd()` 三层切分** → `must`（岗位职责 + 岗位要求）／`pref`（含「…者优先」）／`plus`（加分项段）
   - 段标题切换级别；行内「优先」只降级**该行**，不改变段落级别
   - **「优先」落在括号内时只降级括号子句**（`_split_pref_clause()`）——「3-5年产品经验(平台类、SaaS类产品优先)」的年限是硬要求，不能连坐降级
2. **`SKILL_ATOMS` 47 个细粒度技能点** → 每个带 `(patterns, route, note)`。`route` 决定缺口出口：

   | route | 含义 | 出口 |
   |---|---|---|
   | `learn` | 可短周期补的技术栈 | 学习清单（学完能写进简历，可验证） |
   | `drill` | 面试高频概念 | 讲清楚原理/取舍/踩坑，不必精通到能实现 |
   | `cover` | 硬资质经验（CFA/年限/英文论文） | **不在简历里假装有**，用作品集 + 迁移经验覆盖 |
   | `''` | 通用产品能力 | 按目标公司类型取舍 |

**必备层覆盖率**是**独立指标，不进匹配分**——「这岗我命中多」和「这岗的硬门槛我够了」是两件事，混在一起会让刚调平的权重再次翻桌。写入 META 的 `must=命中/必备总数`，榜单呈现为「必备层」列，<50% 标 ⚠️。脚本还会打印「必备层缺口按出口分流」的三段清单。

> **ASCII 词边界纪律（踩过两次）**：英文 pattern 一律用 `(?<![A-Za-z0-9])X(?![A-Za-z0-9])`，**不要用 `\b`**——Python Unicode 模式下中文算单词字符，`\bRAG\b` 匹配不了「RAG系统」「使用RAG架构」。反例也已坐实：`AML` 撞 `Streamlit`、`CPA` 撞 `CPaaS`、`RAGs?` 撞 `Ragas`。
> **改词表前先量影响面**：`PREF_MARKS`、`SOFT_KEYWORDS`、`SKILL_ATOMS` 都是尺子，改完必须 `rescore_pool.py --apply` 全量重跑并跑防回归自检。

### 跨 JD 能力雷达（skill_radar.py，P2）

**单份 JD 的缺口是个例；N 份 JD 重复出现的缺口才是市场信号。** 学习优先级应该由市场频次决定，不是「哪个顺眼学哪个」。

```
python scripts/skill_radar.py                 # → jd-pool/SKILL_RADAR.md
python scripts/skill_radar.py --min-jd 2      # 只看被 ≥2 份 JD 提及的
python scripts/skill_radar.py --feed-coach    # 额外导出 jd-pool/coach_feed.md
```

- 学习优先级 = **必备层份数×3 + 优先层×2 + 加分项×1**（`DEMAND_W`，注释里有取值理由）
- **按 JD 份数去重，不按词频**——补录过的档案里原始快照与补录段并存，按词频统计会全线虚高
- 输出五段：① 该学什么（再分「事实库有证据 → 改简历即可」／「真缺口 → 真去学」）
  ② 该讲清楚什么（面试概念）③ 该用什么覆盖（硬资质）④ 通用产品能力 ⑤ 已具备（简历弹药，按频次往前提）
- `--feed-coach` **只导出到独立文件，不直接改面试教练的 weaknesses.md**——跨技能写文件属外部副作用，由人确认后粘贴

## 三、企业类型判定（组版前强制步骤）

每个 🟢/🟡 岗位在组版前必须先判定企业类型，选对应模板。**判定必须有依据**（JD 原文特征 + 公司公开信息 WebSearch），不凭模型记忆猜；不确定时问用户或降级为通用模板。

| 类型 | 判定特征（任二命中） | 模板 | 核心叙事 |
|---|---|---|---|
| 大厂 | 已知大厂名单（字节/腾讯/阿里/美团/百度/京东/拼多多等）；JD 提「体系化/跨团队/降本增效/OKR」；组织层级描述复杂 | `template_大厂.md` | 体系化方法 + 指标口径严谨 + 跨团队推动力，弱化"一个人全栈" |
| 小型创业公司 | JD 提「从0到1/全栈/扁平/融资轮次/A轮前」；团队规模小；一人多岗描述 | `template_小型创业公司.md` | 0→1 全栈操盘手 + 速度性价比，强调一个人顶一支小团队 |
| 传统银证保 | 公司属银行/证券/保险及其科技子公司/金融科技公司；JD 提「合规/风控/监管/信贷/展业」 | `template_传统银证保.md` | 金融场景 9 年连续性 + 合规落地实战（护城河），弱化"转型" |
| 互联网企业 | 非大厂梯队的互联网公司/独角兽/垂直平台；JD 提「增长/迭代/数据驱动/AB实验」 | `template_互联网企业.md` | 数据驱动 + AI 落地 + 量化结果前置 |
| 通用 | 特征不足判定，或用户指定 | `resumes/baseline_v4.md` | 现行基线 |

判定结果记入该岗位的 jd-pool 文件（`- 企业类型：大厂 → template_大厂.md`），一岗一版产出时在台账「本版改了什么」里同步记录用了哪套模板。

## 四、一岗一版组版流程

1. **读事实库**：profile（定位摘要）+ experiences/projects（按收录决议筛）+ metrics（数字只从 M-xx 引用）
2. **JD 关键词 → tag 映射**：从 tags.md 体系筛出命中条目，未命中的条目不硬塞
3. **选模板并组版**：按企业类型判定选 templates/ 模板（含头部组版侧重注释，组版时删除），替换/增删条目，**一页硬约束**
4. **ATS 自检**：跑 `ats_check.py <简历.html> --jd <JD文件>`——
   - 格式层：无图标字体、无 CSS grid/多栏、无 svg/canvas、无彩块白字、无待补占位（母版 baseline 豁免）
   - 内容层（2026-09-10 增）：关键词堆砌（单词形 > 1% 词元数）、首屏 6 秒（摘要首段含目标岗关键词）、
     每条经历/项目是否带量化数字、篇幅词元数（**只提示不判失败**——一页取决于字号排版，以 Ctrl+P 预览为准）
   - `--no-content` 只跑格式层；不传 `--jd` 则用通用词表
   - 导出 PDF 后文本层要可复制（记事本能通顺读完 = AI 能读懂）
5. **产出**：`resumes/公司_岗位_YYYYMMDD.md` + `.html`；用户自行 Ctrl+P 导出 PDF（投递物唯一格式是 PDF，不投 HTML/md）
6. **记台账**：pipeline.csv 追加一行，**「本版改了什么」必填**——三周后腾讯打来电话，你必须记得自己简历上写了什么说法（防版本漂移面试翻车）
7. **投递前校对（人工 + RAG 建议，定稿环节）**：产出后**不直接投**——用户人工校对全文；AI 同步生成「投递前优化建议清单」，建议来源必须是检索而非记忆：
   - **本地 RAG**：references/ 策略文档（简历打法/JD关键词对照）+ **career-facts/metrics.md（数字唯一真源，2026-09-10 起取代已归档的 references/数字补全表.md）** + career-facts 事实库（Bad Case、空窗期口径禁忌）+ pipeline.csv 历史复盘备注
   - ⚠️ `references/archive/` 下是已应用完毕/已过期的一次性产物，**不作为 RAG 源**（引用会拿到过期口径）
   - **IMA 摘要级检索**（辅助）：行业简历趋势、目标公司洞察（只引摘要，标注「IMA 摘要级引用」）
   - 建议清单四项：① 事实核对（每个数字回指 M-xx 口径，无来源数字标红）② 说法风险（对照 Bad Case 复盘与空窗期禁忌逐条过）③ JD 关键词遗漏项（软匹配未命中的关键词，能补则补、不能补说明理由）④ ATS 残留风险
   - 用户逐条确认/采纳后才算定稿；确认记录写入台账「本版改了什么」

## 五、投递台账与复盘

- `pipeline.csv` 字段：公司｜岗位｜JD链接｜档位｜投递日｜版本文件｜**本版改了什么（含所用模板）**｜状态（待投/已投/已读/约面/挂/别投）｜下次跟进日｜复盘备注
- 用户说「XX家挂了/约面了」→ 更新状态；挂了时问一句挂在哪轮，回喂 references/ 待人工查阅或面试技能弱项
- 约 face → 提示用户切到 ai-pm-interview-coach 做目标公司定制训练（共享 career-facts，项目叙事口径一致）

## 六、待人工查阅清单（权限墙工作流）

IMA 命中但取不到全文的文档 → 记入 `references/待人工查阅.md`（标题+库名+一句话价值判断）。用户在 ima 客户端能打开，读完把要点回喂，走喂料通道入库。**权限墙只是多一道工序，不是死路。**

## 启动行为

用户说「**找岗/搜岗位**」→ 走「一、主动找岗流程」（手动触发，支持定语，跑完刷新 RANKED_LIST.md 并汇报摘要）；
用户说「**给XX组一版 / 针对XX岗位出简历**」→ 从 RANKED_LIST.md 定位该岗位的 jd-pool 文件（不在池中则先请用户给 JD 或补搜）→ 走「四、一岗一版组版流程」（企业类型判定 → 选模板 → 产出 → 投递前校对）；
用户说「**清理岗位池/清一下池子**」→ 跑 `cleanup_pool.py` 先出 dry-run 预览（过时/冗余清单），**用户确认后**才加 `--apply` 执行，执行完重跑 rank_pool.py 刷新；
用户说「**校验链接/链接还有效吗**」→ 删 `jd-pool/.link_cache.json` 后重跑 `rank_pool.py`（缓存按天失效，同一天不重复请求）；
用户说「**投简历/分析这个JD/看看投递进度/看看推荐list**」时：
1. 读 career-facts 5 文件（含决议表）
2. 按需走上述对应流程；涉及市场判断先联网搜（三通道），不凭记忆；「推荐list」直接展示 jd-pool/RANKED_LIST.md 摘要
3. 产出一律落文件（jd-pool/ resumes/ pipeline.csv），对话里只给摘要

用户说「**我该学什么/缺口在哪/怎么规划学习/准备面试重点**」时 → 跑 `python scripts/skill_radar.py --feed-coach`，
展示 jd-pool/SKILL_RADAR.md 的三路分流结论（该学 / 该讲清楚 / 该覆盖），**不要凭印象给学习建议**——
优先级由 JD 池的真实频次决定。面试概念类可提示用户把 coach_feed.md 粘贴进 ai-pm-interview-coach。

用户说「**这个 JD 的技能要求/这段截图**」并贴了图或文本 → 先 `patch_jd.py --from-file`（或 `--refetch`）补录进对应档案，
再 `rescore_pool.py --apply` 重算。**残缺 JD 报的「缺口 0」是假阴性**，补录前不要下任何匹配度结论。
