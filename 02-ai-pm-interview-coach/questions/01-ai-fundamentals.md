### Q1-01｜用产品经理能听懂的话解释大模型（LLM）的工作原理
- 难度：★★ ｜ 考察点：LLM原理、技术翻译能力
- 参考要点：
  - 本质：超大规模的"下一词预测器"——基于海量文本学习词语间的统计规律，逐 token 生成
  - 关键特征：生成是概率性的（同一问题多次回答可能不同），这是产品设计的核心约束
  - 产品语言翻译：模型没有"查询数据库"，它输出的是"最合理的续写"，所以会有幻觉
  - 加分项：能顺势讲出这对产品设计的影响——需要兜底、需要溯源、需要置信度表达

### Q1-02｜Transformer 和注意力机制是什么？为什么它让 AI 产品爆发？
- 难度：★★★ ｜ 考察点：Transformer、注意力机制
- 参考要点：
  - 注意力机制：处理每个词时动态分配对上下文其他词的"关注度"，解决长距离依赖
  - 并行计算：不同于 RNN 逐词串行，Transformer 可并行训练，才有了"大力出奇迹"的规模定律
  - 产品视角：能力随参数/数据/算力规模可预测地提升（Scaling Law），让"先做产品再等模型变强"成为可能
  - 加分项：知道上下文窗口就是注意力机制的代价（计算量随长度平方增长）

### Q1-03｜什么是 RAG？它的架构组成和适用场景？
- 难度：★★ ｜ 考察点：RAG、检索增强生成
- 参考要点：
  - 定义：检索增强生成——先从知识库检索相关片段，再让模型基于片段作答
  - 五步链路：文档切分 → 向量化 → 检索 → 拼装 Prompt → 生成回答
  - 解决什么：知识时效性（模型训练截止后的事）、私域知识（模型没见过的）、可溯源（降低幻觉）
  - 适用判断：知识频繁更新/需要引用出处 → RAG；任务模式固定/知识稳定 → 微调可能更优
  - 加分项：能说出 RAG 失败模式——检索不到（召回问题）、检索到但没用上（排序/生成问题）

### Q1-04｜RAG 和微调（Fine-tuning）如何选型？
- 难度：★★★ ｜ 考察点：RAG vs 微调、技术选型
- 参考要点：
  - 先答本质区别：RAG 是"开卷考试"（外挂知识），微调是"岗前培训"（改变行为模式）
  - 选 RAG 的信号：知识常更新、要溯源、需要权限隔离（不同用户看不同文档）
  - 选微调的信号：输出格式/风格/语气需强控制、领域术语特殊、要把长 prompt 固化省成本
  - 产品经理答法：这不是二选一，很多生产系统 RAG+微调叠加；关键是先明确"知识问题还是行为问题"
  - 加分项：提成本维度——RAG 边际成本在检索侧，微调成本在训练+维护数据集

### Q1-05｜什么是 AI Agent？它和普通聊天机器人的本质区别？
- 难度：★★★ ｜ 考察点：Agent、ReAct、工具调用
- 参考要点：
  - 本质区别：chatbot 是"一问一答"，Agent 是"给目标、自主规划多步执行"——感知→规划→行动→反思循环
  - 核心组件：规划（任务拆解）、工具调用（Function Calling）、记忆（短期上下文+长期存储）、反思（自我纠错）
  - 典型模式：ReAct（推理+行动交替）是当前主流范式
  - 产品视角：Agent 把交互从"轮次"变成"任务"，考核指标从回答质量变成任务完成率
  - 加分项：知道 Agent 的代价——步数多、成本高、错误累积，所以高价值低容错场景要人审（human-in-the-loop）
  - 加分项2：工程生态认知——LangChain/LangGraph 等编排框架降低 Agent 搭建门槛，但生产系统多为自研轻量编排；被问"用过什么框架"时诚实回答并展示对框架局限的理解（100题集补充）

### Q1-06｜Prompt Engineering 有哪些常用技巧？它是产品能力还是用户能力？
- 难度：★★ ｜ 考察点：提示工程
- 参考要点：
  - 技巧分层：角色设定、少样本示例（few-shot）、思维链（CoT，"一步步想"）、结构化输出约束、拆解复杂任务
  - 产品视角核心：好的 AI 产品把 prompt 工程做进产品里——用户说自然语言，产品负责翻译成高质量指令
  - 反例警示：要求用户写复杂 prompt 的产品是"半成品"，prompt 复杂度是转嫁给用户的成本
  - 加分项：提到 prompt 的版本管理与评测——prompt 改一个词效果可能大变，需要像代码一样测试上线

### Q1-07｜大模型幻觉是什么？产品层面有哪些缓解手段？
- 难度：★★★ ｜ 考察点：幻觉、产品兜底设计
- 参考要点：
  - 定义：模型一本正经地编造事实，根源是它做的是概率续写而非事实查询
  - 产品层缓解：RAG 溯源（回答附引用）、置信度表达（不确定就说不确定）、输出校验（关键信息走规则/数据库比对）
  - 场景区分：创意场景幻觉可接受甚至加分；事实场景（医疗/法律/金融）零容忍——按场景分级设计
  - 交互设计：展示引用来源、让用户易于验证、高危操作加确认
  - 应急框架（幻觉已成事实时）：事前预防（RAG/上下文工程供准确来源+免责声明）→ 事中拦截（敏感词过滤+一键反馈入口）→ 事后复盘（badcase 归因反哺模型与数据）（PMTalk 面经补充）
  - 加分项：承认幻觉无法根除，产品设计目标是"管理幻觉的代价"而非消灭幻觉

### Q1-08｜Token 和上下文窗口是什么？长上下文带来哪些产品机会与挑战？
- 难度：★★ ｜ 考察点：token、context window
- 参考要点：
  - Token：模型处理文本的最小单位，中文约 1 字≈1-2 token；API 按 token 计费，成本核算的基础
  - 上下文窗口：模型一次能"看到"的最大 token 数，决定单次能处理的信息量
  - 机会：整本书分析、超长文档问答、全代码库理解
  - 挑战：长上下文中部信息易被忽略（lost in the middle）、成本随长度线性涨、响应变慢
  - 加分项：产品策略——窗口大≠全塞进去，检索（RAG）+压缩摘要往往比硬塞更便宜更好

### Q1-09｜多模态大模型是什么？举三个产品场景说明其价值
- 难度：★★ ｜ 考察点：多模态
- 参考要点：
  - 定义：能同时理解/生成多种模态（文本、图像、语音、视频）的模型
  - 场景一：视觉问答/客服——用户拍照问"这个报错怎么解决"，免文字描述门槛
  - 场景二：内容生产——图生文（素材管理、电商详情页）、文生图（营销素材）
  - 场景三：无障碍/适老化——语音+视觉交互降低使用门槛，扩大用户群
  - 加分项：指出多模态的核心产品价值是"输入输出门槛的降低"，而不只是酷炫
  - 加分项2：内容生产演进视角——UGC（人人创作）→ PGC（专业机构）→ AIGC（机器量产），多模态补齐图像/音视频短板后，"UGC 无戏、PGC 可战"的内容格局正在被改写（100题集补充）

### Q1-10｜如何评估一个 LLM 应用的好坏？设计一套评测方案
- 难度：★★★★ ｜ 考察点：模型评测、Eval体系
- 参考要点：
  - 先分维度：准确性、相关性、完整性、安全性/合规、时延、成本——不同产品权重不同
  - 方法栈：人工评审（金标准但贵）→ LLM-as-Judge（用强模型打分，需防偏置）→ 自动化指标（如引用命中率）→ 用户行为信号（采纳率、复制率、追问率）
  - 工程关键：建评测集（Golden Set）——100~500条覆盖典型场景的标注数据，每次改动跑回归
  - 产品经理角色：定义"什么算好"的边界 case，而不是只看平均分
  - 加分项：提到线上 A/B 与离线评测结合；评测集要随用户真实 badcase 持续补充

### Q1-11｜Embedding 和向量数据库是什么？在产品里起什么作用？
- 难度：★★★ ｜ 考察点：embedding、向量检索
- 参考要点：
  - Embedding：把文本/图片映射成高维向量，语义相近则向量距离近——"语义坐标"
  - 向量数据库：存向量并支持近似最近邻检索（如 Milvus、pgvector），实现"按语义找"而非"按关键词找"
  - 产品作用：语义搜索、推荐召回、RAG 的检索层、去重与聚类
  - 与关键词搜索对比：用户搜"怎么让猫不拆家"，关键词匹配可能漏掉"防止猫抓沙发"，语义检索能召回
  - 加分项：知道混合检索（向量+关键词）是生产标配，纯向量会漏专有名词

### Q1-12｜SFT 和 RLHF 是什么？"对齐"为什么对产品重要？
- 难度：★★★ ｜ 考察点：SFT、RLHF、对齐
- 参考要点：
  - SFT（监督微调）：用人工标注的高质量问答对教模型"该怎么答"
  - RLHF（人类反馈强化学习）：人类对多个回答排序，训练奖励模型，让模型输出更符合人类偏好
  - 对齐：让模型行为符合人类意图与价值观——有用、诚实、无害
  - 产品重要性：对齐决定"模型人格"——同一底座模型，不同对齐策略产生不同产品体验（安全尺度、语气、拒答边界）
  - 加分项：能举例对齐的两难——过度拒答（不有用）vs 不够安全（有风险），产品要定义自己场景的平衡点

### Q1-13｜模型参数量、推理成本与产品体验如何权衡？
- 难度：★★★ ｜ 考察点：成本、模型选型、权衡
- 参考要点：
  - 基本规律：参数越大能力越强，但时延和成本越高——体验三角：质量、速度、价格
  - 分级路由策略：简单请求走小模型/规则，复杂请求走大模型（如先分类再路由），成本可降一个量级
  - 缓存策略：高频问题缓存答案，语义缓存（相似问题命中缓存）
  - 场景定标：不是所有场景都需要最强模型——摘要用小模型够用，复杂推理才上大模型
  - 加分项：给出成本公式意识——单次成本×调用量×频率，PM 要能算清单位经济模型（unit economics）

### Q1-14｜什么场景下值得做微调？数据准备有哪些要求？
- 难度：★★★ ｜ 考察点：微调决策、数据要求
- 参考要点：
  - 值得做的信号：prompt 已调到极致仍不达标、需要稳定的风格/格式、领域语料巨大且私有、高频调用下长 prompt 成本过高
  - 不值得的信号：知识更新频繁（用 RAG）、样本太少、需求还没验证稳定
  - 数据要求：数千到数万条高质量样本；多样性>数量；标注一致性要抽检；留出测试集
  - 迭代方式：先小规模实验→评测集验证→对比基线（纯 prompt 方案），证明有显著提升再全量
  - 加分项：提醒微调不是一劳永逸——底座模型升级后可能要重训，维护成本要算进决策

### Q1-15｜什么是 AI 原生应用？和"套壳"应用的本质区别？
- 难度：★★★ ｜ 考察点：AI native、产品差异化
- 参考要点：
  - 套壳：把模型 API 包一层 UI，模型可替换、产品无积累——壁垒趋近于零
  - AI 原生：产品逻辑围绕 AI 能力与约束重新设计，而非给旧流程加个 AI 按钮
  - 三个标志：交互为 AI 重构（对话/生成式 UI）、数据飞轮（用户使用产生独有数据反哺产品）、工作流深度整合（嵌入业务链路而非独立玩具）
  - 本质区别在"积累物"：套壳的积累是用户量，AI 原生的积累是数据、工作流、评测体系
  - 加分项：辩证补一句——套壳不丢人，关键是有没有沉淀别人拿不走的东西（场景理解/私有数据/网络效应）

### Q1-16｜思维链（CoT）提示：原理、适用场景与局限
- 难度：★★★ ｜ 考察点：CoT、提示工程深水区
- 参考要点：
  - 定义：让模型"一步步想"再给答案——把复杂问题拆成中间推理步骤，本质是让模型自己生成"垫脚石"式上下文，提升最终答案质量
  - 与标准提示学习的区别：few-shot 学的是"答案模式"，CoT 学的是"推理过程"；需要人为拆解示范步骤防止跑偏
  - 为什么有效：模型逐 token 生成，中间步骤为后续推理提供高质量上下文，复杂推理能力被"过程"激活
  - 适用：数学/逻辑/多步决策几乎全场景可用；简单任务用 Step-Back（先抽象再回答）性价比更高
  - 局限要主动讲：推理过程错了结论更糟（错误链放大）；token 消耗与响应时长显著增加
  - 加分项：呼应研究前沿——RL 训练推理模型（如 R1）正是让模型自我生成思维链数据，过程对错信号赋予模型判断力
- 来源：用户提供（2026-09-07）· 人人都是产品经理〈2万字拆解100道AI产品经理面试题〉（原文 CoT 七连问合并为一题）

### Q1-18｜为什么大模型输入 token 单价比输出低？
- 难度：★★★ ｜ 考察点：成本结构、原理理解
- 参考要点：
  - 输入是"一次性"并行计算：prompt 进来一次 prefill 处理完，GPU 利用率高，成本摊薄
  - 输出是"逐 token"串行生成：每生成一个 token 都要对全部已有序列（含整个 prompt+已生成部分）重算注意力——每个输出 token 都在为全部历史付费
  - 产品含义：长 prompt+短输出的应用成本结构好（分类/抽取类）；短 prompt+长输出（写作生成类）成本高——这决定定价与产品形态
  - 加分项：引申到缓存定价——provider 对重复 prompt 前缀给折扣（KV cache 复用），产品里固定系统提示词放前面可省钱
- 来源：用户提供（2026-09-07）· 人人都是产品经理〈2万字拆解100道AI产品经理面试题〉

### Q1-19｜DeepSeek R1 类推理模型适合在 AI 产品的哪些环节使用？
- 难度：★★★ ｜ 考察点：推理模型、模型选型
- 参考要点：
  - 推理模型特征：生成前先"长思考"（可见思维链），强在数学/代码/复杂分析，弱在响应速度与成本
  - 适合环节：复杂分析类任务（深度研报解读、多条件决策）、创意发散与交叉联想、高质量数据蒸馏（用 R1 生成数据喂小模型）
  - 不适合环节：高并发实时交互（思考时间不可接受）、简单分类抽取（大炮打蚊子）、Function Calling 密集的 Agent 执行层（部分推理模型不支持工具调用且慢）
  - 产品策略：推理模型当"大脑"（规划/复核），轻量模型当"手脚"（执行/路由）——混合架构是务实解
  - 加分项：说清"思考预算"概念——按任务难度动态决定是否触发深度推理，成本与质量平衡

### Q1-20｜Prompt 工程的局限性是什么？
- 难度：★★★ ｜ 考察点：prompt边界、技术判断力
- 参考要点：
  - 能力边界：prompt 只能激活模型已有能力，不能注入新知识（要 RAG）也不能稳定改变行为模式（要微调）——"提示词调不出来的，换方法别硬调"
  - 稳定性边界：对措辞极度敏感、跨模型不可迁移、长 prompt 内多条指令互相打架——缺乏工程级的确定性
  - 人的边界：写好 prompt 依赖写手的见识与表达能力，效果难量化归因，团队协作难沉淀
  - 工程视角：ToC 产品不该把能力押在用户 prompt 水平上；ToB 生产系统里 prompt 只是手段之一，RAG/工具调用/护栏共同构成可靠性
  - 加分项：判断框架——效果不好时先区分"模型边界问题/提示词问题/工程问题"，三类问题药方完全不同

### Q1-21｜什么是 MCP 和 Skill？为什么 2026 年它成了 Agent 平台 PM 的必备认知？
- 难度：★★★ ｜ 考察点：MCP、Skill、Agent 生态标准化
- 参考要点：
  - MCP（Model Context Protocol）解决工具接入碎片化：无标准时 N 个模型接 N 个工具要写 N×(N-1) 套适配器，有标准后降到 O(N)
  - Skill 是把可复用能力（提示词+工具+流程）封装成标准件，让 Agent 按需加载而非每次重写
  - 产品视角：MCP 让"接哪些工具"从工程问题变成产品选型问题，PM 要能判断接入某个工具的成本收益
  - 加分项：指出标准之战的风险——生态未定型时过早绑定某套协议，迁移成本可能高于收益
- 来源：真题出处：CSDN MCP 技术社区〈多智能体与 MCP 成为事实标准〉https://mcp.csdn.net/6a75caea662f9a54cb99790e.html（2026-08-07）

### Q1-22｜端侧模型（如 30B 级本地模型）相比云端的核心优势与受限场景是什么？
- 难度：★★★ ｜ 考察点：端云协同、隐私、成本结构
- 参考要点：
  - 优势四件套：数据不出设备（隐私合规）、零网络延迟、离线可用、边际成本为零（不按 token 付费）
  - 受限场景：能力弱于旗舰云端模型、复杂推理与长上下文跑不动、设备算力与内存限制、模型更新需发版
  - 判断框架：按"任务难度 × 数据敏感度 × 使用频次"三象限分——高频+敏感+简单任务放端侧，复杂任务上云
  - 加分项：混合路由是主流解法——端侧先处理，置信度不足或任务复杂时无缝转云
